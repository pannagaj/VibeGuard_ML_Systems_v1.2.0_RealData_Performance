# Model card: VibeGuard VibrationMLP

## Summary

VibeGuard VibrationMLP is a compact feed-forward classifier over 20 engineered vibration features. It predicts one of four labels: `healthy`, `imbalance`, `misalignment`, or `bearing_fault`.

## Intended use

- Demonstrate a reproducible Python/PyTorch training and inference system.
- Exercise numerical feature engineering, baseline comparison, model artifact versioning, API deployment, and inference optimization.
- Serve as a portfolio project and a starting point for experiments on a labelled vibration dataset.

## Out-of-scope use

- Safety-critical fault detection or automatic machine shutdown.
- Maintenance decisions without independent engineering review.
- Claiming validated industrial performance based on synthetic data.

## Data

The built-in generator simulates a 1,024 Hz, 512-sample vibration window with a rotating fundamental, harmonics, additive noise, and class-specific changes. Bearing-fault examples contain decaying resonant impulses. Every sample is generated from a fixed seed and carries a synthetic label.

This generator is illustrative, not a physical motor simulator. It cannot represent all shaft speeds, sensor placement, motor types, mounting resonances, load states, environmental noise, fault severities, domain shifts, or sensor calibration errors.

## Inputs and outputs

- Input: one or more ordered vectors of 20 finite engineered features, or a raw time-domain window with known sample rate and fundamental frequency.
- Output: one of four class labels, class scores, and the maximum score as a confidence-like value.
- The maximum softmax score is not calibrated confidence and must not be interpreted as a verified probability of correctness.

## Training and evaluation

- Seeded stratified train/validation/test splits (64/16/20).
- StandardScaler fitted only on the training split.
- AdamW, cross-entropy, gradient clipping, finite-loss checks, and validation-loss early stopping.
- ExtraTreesClassifier comparison using the same training/test split.
- Report accuracy, macro precision, macro recall, macro F1, log loss, per-class metrics, and confusion matrix.

Metrics are generated by running the pipeline in the target environment and saved to `artifacts/`. There are intentionally no prewritten performance claims in this card.

## Known limitations and risks

- Synthetic-to-real domain gap is unknown and likely substantial.
- Feature distributions may change with sampling rates, sensor mounting, operating RPM and physical equipment.
- Labels are only as reliable as source annotation; this demo's labels are generated by the simulator.
- A low-confidence or high-confidence output is not a safety diagnosis.
- The API has no authentication, rate limiting, audit logging or access control by default.

## Monitoring before real deployment

A real deployment should include sensor/data quality checks, data and label lineage, per-machine and per-operating-condition evaluation, calibration analysis, out-of-distribution monitoring, drift monitoring, rollback controls, auditability, human review and fail-safe procedures designed with domain engineers.

## Ethical and operational considerations

Use only sensor data that the operator is authorized to collect and process. Retain source metadata and label provenance. Do not silently convert model predictions into safety-critical action.
